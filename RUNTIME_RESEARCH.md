# LLM deployment runtime research

Verified against the official documentation on 2026-10-11. These are candidate experiment controls, not universal recommended values. The serving study covers vLLM and SGLang alongside the separately measured llama.cpp path. Unsloth prepares artifacts; Ollama supplies the existing local coding model only. Pin the installed runtime version, model revision, quantization, chat template, hardware, drivers, and workload before comparing results.

## MoE opportunity experiments

1. **GPU memory ceiling:** hold checkpoint, workload, and output quality constant. Compare baseline KV precision and context/concurrency against quantized KV, smaller cache, and quantized weights when the model/runtime supports them. Record GPU memory peak, time to first token (TTFT), inter token latency (ITL), throughput, OOMs, and quality checks. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/), [SGLang server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)
2. **Expert skew across multiple GPUs:** compare tensor parallel baseline with expert parallelism, then test load balancing and communication backends one change at a time. Measure per GPU occupancy, expert balance, all to all time, TTFT, ITL, and throughput. EP is a multi GPU distribution technique; it does not make a single GPU's full model automatically fit. [vLLM expert parallel deployment](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/), [SGLang expert parallelism](https://docs.sglang.io/docs/advanced_features/expert_parallelism)
3. **RAM headroom:** compare no offload to explicit CPU weight offload budgets after checking host RAM and CPU to GPU bandwidth. Record page faults, swap, transfer stalls, TTFT, ITL, and throughput. Distinguish weight offload from KV offload; vLLM documents separate `--cpu-offload-gb` and `--kv-offloading-size` controls. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/), [SGLang server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)
4. **SSD and startup:** record checkpoint bytes, cold load time, warm load time, peak disk throughput, and free space. Compare local SSD placement and vLLM's `--enable-ep-weight-filter` only for a compatible per expert checkpoint. Avoid claiming faster decode from faster storage without measured runtime I/O. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/)

## Evidence log for each trial

Save the exact command/environment and runtime version, model and tokenizer revision, quantization format, chat template, driver/GPU/RAM/SSD inventory, workload prompt/output length distribution, concurrency and request rate. Record success or failure and the limiting resource. Use repeated runs with cold and warm starts separated. vLLM and SGLang provide serving benchmark tools for controlled loads. [vLLM bench serve](https://docs.vllm.ai/en/latest/cli/bench/serve/), [SGLang bench serving](https://docs.sglang.io/docs/developer_guide/bench_serving)

For a possible improvement beyond the measured llama.cpp placement knob, see the [Strata and Maya policy research](STRATA_MAYA_RESEARCH.md). Their expert-tier approaches require compatible engine support and a controlled benchmark before a speed claim.
