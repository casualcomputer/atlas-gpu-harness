# LLM deployment runtime research

Verified against the official documentation on 2026-10-11. These are candidate experiment controls, not universal recommended values. Pin the installed runtime version, model revision, quantization, chat template, hardware, drivers, and workload before comparing results.

| Runtime | Supported controls worth testing | Important limits |
| --- | --- | --- |
| vLLM | `--gpu-memory-utilization`, `--kv-cache-memory-bytes`, `--kv-cache-dtype`, `--max-num-batched-tokens`, `--max-num-seqs`, `--cpu-offload-gb`; for MoE, `--enable-expert-parallel`, `--all2all-backend`, and `--enable-eplb`. [Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/) | Explicit KV cache bytes override GPU utilization for KV sizing. CPU weight offload needs a fast CPU to GPU interconnect. `--enable-ep-weight-filter` can reduce disk reads only when the checkpoint stores per expert tensors; it has no effect on some fused expert layouts. [Engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/) |
| SGLang | `--mem-fraction-static` sets the weights plus KV pool budget; `--max-running-requests` limits concurrency. Test `--kv-cache-dtype`, `--cpu-offload-gb`, `--ep-size`, `--moe-a2a-backend`, `--moe-runner-backend`, and `--enable-eplb` where supported. [Server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments), [expert parallelism](https://docs.sglang.io/docs/advanced_features/expert_parallelism) | Reserve room for activations and CUDA graphs. FP8 KV cache may need supplied scaling factors for accuracy. Backend choices depend on model, device, and installed libraries. [Hyperparameter tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning), [server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments) |
| Ollama | `OLLAMA_CONTEXT_LENGTH`, `OLLAMA_NUM_PARALLEL`, `OLLAMA_MAX_LOADED_MODELS`, `OLLAMA_KEEP_ALIVE`, `OLLAMA_FLASH_ATTENTION`, `OLLAMA_KV_CACHE_TYPE`, `OLLAMA_MODELS`, and per request `num_ctx`/`keep_alive`. `ollama ps` shows the CPU/GPU weight split. [FAQ](https://docs.ollama.com/faq) | Required RAM scales with parallel requests and context length. Quantized KV cache requires Flash Attention, is a server wide setting, and trades precision for capacity. `OLLAMA_MODELS` changes the model storage directory; SSD placement is a load and capacity experiment, not a documented direct decode speed control. [FAQ](https://docs.ollama.com/faq) |
| Unsloth | Treat it as a model source and export workflow, not an equivalent serving scheduler. Its documented vLLM route exports merged 16 bit weights or LoRA adapters and then serves with vLLM; its GGUF route can serve through Ollama. [vLLM guide](https://unsloth.ai/docs/basics/inference-and-deployment/vllm-guide.md), [saving to GGUF](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-gguf) | Keep the training chat template and special token behavior when deploying exports. Otherwise a model that worked in Unsloth may produce poor or repetitive output in vLLM or Ollama. Validate quality alongside speed. [Troubleshooting](https://unsloth.ai/docs/basics/saving-and-using-models/troubleshooting) |

## MoE opportunity experiments

1. **GPU memory ceiling:** hold checkpoint, workload, and output quality constant. Compare baseline KV precision and context/concurrency against quantized KV, smaller cache, and quantized weights when the model/runtime supports them. Record GPU memory peak, time to first token (TTFT), inter token latency (ITL), throughput, OOMs, and quality checks. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/), [SGLang server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments), [Ollama FAQ](https://docs.ollama.com/faq)
2. **Expert skew across multiple GPUs:** compare tensor parallel baseline with expert parallelism, then test load balancing and communication backends one change at a time. Measure per GPU occupancy, expert balance, all to all time, TTFT, ITL, and throughput. EP is a multi GPU distribution technique; it does not make a single GPU's full model automatically fit. [vLLM expert parallel deployment](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/), [SGLang expert parallelism](https://docs.sglang.io/docs/advanced_features/expert_parallelism)
3. **RAM headroom:** compare no offload to explicit CPU weight offload budgets after checking host RAM and CPU to GPU bandwidth. Record page faults, swap, transfer stalls, TTFT, ITL, and throughput. Distinguish weight offload from KV offload; vLLM documents separate `--cpu-offload-gb` and `--kv-offloading-size` controls. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/), [SGLang server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)
4. **SSD and startup:** record checkpoint bytes, cold load time, warm load time, peak disk throughput, and free space. Compare local SSD placement and vLLM's `--enable-ep-weight-filter` only for a compatible per expert checkpoint. Avoid claiming faster decode from faster storage without measured runtime I/O. [vLLM engine arguments](https://docs.vllm.ai/en/latest/configuration/engine_args/), [Ollama FAQ](https://docs.ollama.com/faq)

## Evidence log for each trial

Save the exact command/environment and runtime version, model and tokenizer revision, quantization format, chat template, driver/GPU/RAM/SSD inventory, workload prompt/output length distribution, concurrency and request rate. Record success or failure and the limiting resource. Use repeated runs with cold and warm starts separated. Ollama's generate API reports `load_duration`, `prompt_eval_count`/`duration`, and `eval_count`/`duration`; vLLM and SGLang provide serving benchmark tools for controlled loads. [Ollama generate API](https://docs.ollama.com/api/generate), [vLLM bench serve](https://docs.vllm.ai/en/latest/cli/bench/serve/), [SGLang bench serving](https://docs.sglang.io/docs/developer_guide/bench_serving)
