The LLM deployment agent that never forgets an experiment.

It launches an open model on a real inference engine, tries configurations, and checks every answer, memory peak and speed. Every result is written to MongoDB Atlas before the next step, and every new attempt starts from what Atlas returns. A setting is promoted only if it beats the engine default on questions it has never seen.

The problem

Today, deployment is tuned by hand — or prompt by prompt.

LLM infra engineers run a benchmark, paste the output into a chat assistant, try the next suggestion, and repeat. The assistant can't run anything, can't verify an answer, forgets what failed last session, and can't tell a real speedup from noise.

How it works

A controlled experiment loop, not a guess.

The agent proposes; the harness decides. Each step writes to or reads from Atlas, so a crashed run resumes from what was proven and the next proposal starts from real measurements.

Inspect

Read model metadata, GPU, RAM and engine version.

Baseline

Measure the engine's own default first, under a fixed contract.

Propose

A coding model writes the placement policy as constrained Python.

Benchmark

Run the real model. Check every answer, sample memory, measure speed.

Atlas

Commit results, failures and the evidence each decision used.

The agent can change only what it's allowed to change. Model file, engine, context, threads, decoding, answer rules and acceptance thresholds are locked by the harness. A compatibility fingerprint of GPU, driver, engine and model stops evidence from being reused where it doesn't apply. Three gates: every answer must be correct, the winner is re-run on unseen questions, and it must beat the engine default by a set margin — or the default stays.
MongoDB Atlas · on the execution path

Atlas is the agent's memory — not a dashboard.

The agent cannot advance until a result is committed, and it cannot propose until it has read prior evidence. Five operations, all in store.py and inference.py:

  1. Claim — each trial gets a deterministic _id and an owner token in experiments; stale completions are rejected.
  2. Commit — answers, memory, speed and errors are written before the loop advances.
  3. Retrieve — the next proposal reads find({context_hash, status}); evidence from a different GPU, engine or model is never reused, and held-out results are hidden.
  4. Cite — every decisions document stores the retrieved_experiment_ids it used; a $lookup audits the trail.
  5. Resume — the runs document restores progress; the finished Kimi run resumed in 7.80 s with nothing re-run.
