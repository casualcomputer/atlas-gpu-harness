Atlas GPU Harness is an autonomous deployment agent for LLM infra teams. Instead of tuning by hand or prompt by prompt, it launches the model on a real engine, benchmarks each configuration for correctness, memory and speed, and records every experiment in MongoDB Atlas — so a setting goes to production only when the evidence holds.

The problem

Today, deployment is tuned by hand — or prompt by prompt.

LLM infra engineers run a benchmark, paste the output into a chat assistant, try the next suggestion, and repeat. The assistant can't run anything, can't verify an answer, forgets what failed last session, and can't tell a real speedup from noise.

Compute is scarce

The cheapest GPU is the one you own

Inference is about two-thirds of AI compute, and DRAM is projected to rise more than 400% from 2024 to the end of 2026. Using existing hardware well is the cheapest capacity there is.

Dependencies everywhere

Model × hardware × engine

Expert offload, GPU layers, KV cache, context, batching — each depends on the GPU, driver, engine version and model architecture. Change one, and you tune again.

False wins

Benchmarks lie quietly

A config can be fast and wrong, or "faster" only because of noise. Without controls, a bad result becomes the baseline for every decision after it.

How it works

A controlled experiment loop, not a guess.

The agent proposes; the harness decides. Each step writes to or reads from Atlas, so a crashed run resumes from what was proven and the next proposal starts from real measurements.

Inspect

Read model metadata, GPU, RAM and engine version.

Baseline

Measure the engine's own default first, under a fixed contract.

Propose

A coding model writes the placement policy as constrained Python.

Benchmark

Run the real model. Check every answer, sample memory, measure speed.

Atlas

Commit results, failures and the evidence each decision used.

The agent can change only what it's allowed to change. Model file, engine, context, threads, decoding, answer rules and acceptance thresholds are locked by the harness. A compatibility fingerprint of GPU, driver, engine and model stops evidence from being reused where it doesn't apply.
Gate 1

Correct or rejected

Exact JSON answer checks on fixed questions. A wrong answer is never counted as fast.

Gate 2

Confirm on unseen questions

The best tuning result is re-run on reserved questions the agent never saw, in reversed order.

Gate 3

Beat the default, clearly

A candidate replaces the engine default only if each confirmation block improves decode speed by more than 5%.

What the agent did, from the Atlas decision log
  • Baseline measured. 47.21 tok/s, 12/12 correct.
  • Policy 1 — hypothesis: "slightly reduce CPU experts to conserve GPU memory." Result: 22.77 tok/s, about 52% slower.
  • Policy 2 read that failure from Atlas: "The previous policy … slowed down inference. Revert to the initial estimate." Result: +30.73% over policy 1.
  • Still 36.94% slower than the default — so the harness did not promote it.
  • Default confirmed on unseen questions. Recipe saved and reused.

Roadmap

From one GPU to every model on every chip.

Atlas is what makes this scale: many agents on many machines need one shared, durable record of what was tested, what failed and what was proven.
