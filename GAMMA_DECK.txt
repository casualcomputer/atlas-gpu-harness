# A deployment agent that remembers its experiments.

Visual: Inspect → Baseline → Agent proposes → Real engine benchmark → MongoDB Atlas → back to Agent proposes
Caption: The agent proposes. The harness checks. Atlas preserves the evidence.
Small: Generated llama.cpp placement policies; separate documented Strata policy sweep.

Speaker notes: In the llama.cpp workflow, a coding model writes a constrained CPU expert-placement policy. The harness runs the real model, checks fixed tasks, samples memory and records timing. It commits the result to MongoDB Atlas before continuing, and the next proposal receives the recorded feedback. A candidate replaces the default only after passing the configured checks on reserved questions. Strata uses a separate fixed sweep of documented runtime settings; those policies were not generated by the coding model.

30 GB on 16 GB — Kimi model files on a consumer GPU. Revised policy +31% versus the first proposal; the faster engine default was retained.
Same Qwen at 32K — llama.cpp 18.22 vs. Strata 107.77 tok/s. 5.92× observed decode throughput; one request each, different runtime settings. Both retrieved 8/8 values; both arithmetic totals mismatched.

Speaker notes: The Kimi run served a 30-gigabyte model file on a 16-gigabyte GPU using llama.cpp's existing offload. Feedback improved the second generated policy by about thirty-one percent over the first, but it remained slower than the engine default. The later Qwen comparison used identical model files and 32K input tokens. Strata generated at 107.77 tokens per second against llama.cpp at 18.22, an observed 5.92 times ratio. Both retrieved all eight values and both returned the same wrong total. This is one request per engine, with different runtime optimizations including Strata MTP and expert skipping; it does not isolate a harness-generated policy gain. In an earlier GPU-operator experiment, access to known failure history reduced attempts from four to three in both blocks. That is a measured reduction in repeated testing, not an LLM throughput gain.

# Atlas connects each decision to its evidence.

Five numbered rows:
1. Claim — owner token guards result writes
2. Commit — save the result before advancing
3. Retrieve — reuse compatible experiment history
4. Cite — store the IDs consulted by each decision
5. Resume — reuse committed results after restart

Small: Demonstrated with one controller per machine; unfinished trials may run again.

Speaker notes: Atlas is on the execution path. The controller claims a trial with an owner token, commits its result, retrieves compatible history, and records the evidence behind its next decision. The context hash includes hardware, engine, source and model identity. We demonstrated stopping after a commit and resuming without repeating that saved work. This is a single-controller demonstration: a trial interrupted before its result is committed may execute again. We do not claim distributed exactly-once execution.
