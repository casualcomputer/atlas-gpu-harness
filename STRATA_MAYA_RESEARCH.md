# Strata and Project Maya: what can be reused and what must be measured

Checked against the projects' first-party documentation on 2026-10-11. These are research findings and proposed experiments, not results produced by this repository.

## Finding

Strata and Project Maya demonstrate concrete MoE runtime ideas that are substantially richer than choosing `n_cpu_moe` in llama.cpp. Their published throughput cannot be presented as an improvement by *this* harness over its Kimi llama.cpp baseline. The engines target different model families, and no Strata or Maya trial on this repository's Kimi GGUF and RTX 5070 Ti has been run. The completed Kimi experiment found that llama.cpp automatic fitting (47.21 decode tokens/s) beat both generated layer-placement policies (22.77 and 29.77 tokens/s); see [our recorded result](INFERENCE_RESULTS.md) and [Atlas export](evidence/inference/70be4572a9824186999857dadeb1237d.json).

| Project | Actual model/runtime scope | Useful optimization mechanisms | Directly runs our Kimi GGUF? |
| --- | --- | --- | --- |
| [Strata](https://github.com/Niko1221/Strata/blob/main/docs/MODELS.md) | Its documentation says it runs **Qwen3.8-Flash-Next** and variants of that model, including several quants and fine-tunes. | Adaptive VRAM expert cache, RAM expert pool, concurrent CPU/GPU missed-expert work, PCIe share, MTP and lookup speculative drafting, prompt chunking, and optional SSD-backed expert tiers. Its `--calibrate` tests PCIe share, draft confidence, CPU workers, and cache adaptation, keeping a setting only if measured decode speed exceeds the default by more than 3%. [Architecture](https://github.com/Niko1221/Strata/blob/main/docs/HOW_IT_WORKS.md), [calibration](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md). | **No documented support.** It is not a generic GGUF backend just because the source models use GGUF files. |
| [Project Maya](https://github.com/mw00/project-maya/blob/main/README.md) | The engine is built for **GLM-5.3-Flash**, with Maya's own ~95–156 GB quants. It is derived from Strata and ggml/llama.cpp components. | An adaptive VRAM/RAM/NVMe expert hierarchy; GPU layer-split planning; CPU-versus-PCIe expert placement; usage-based expert promotion; MTP; SSD read sizing. `--calibrate` tests decode speed on new prompts and records CPU lane, PCIe share, and disk read-chunk choices only when more than 3% faster. The important transferable *policy* is a runtime decision over expert residency and traffic: which experts stay in VRAM, which are computed from RAM, which misses cross PCIe, when the cache adapts, and, where needed, which weights are fetched from NVMe. Our current Kimi policy only chooses the number of early CPU expert layers. That cannot express Strata's or Maya's within-layer per-expert cache. A meaningful Kimi implementation would need a compatible engine extension, not a different value of `n_cpu_moe`. This is an inference from the documented mechanisms and our policy interface, not a measured speed claim. [Strata architecture](https://github.com/Niko1221/Strata/blob/main/docs/HOW_IT_WORKS.md), [Maya settings](https://github.com/mw00/project-maya/blob/main/docs/SETTINGS.md), [our architecture](ARCHITECTURE.md).

## What published performance does and does not establish

- [Strata's RTX 5070 12 GB table](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md) reports approximately 53–94 decode tokens/s for its Qwen3.8-Flash-Next variants on a Ryzen 5 7600/64 GB host, depending on quant. That is a **different model, quant, GPU, host, and workload** from our Kimi measurement; comparing either number to Kimi's 47.21 as a speedup is invalid.
- A [Strata first-party Intel Arc Pro B70 report](https://github.com/Niko1221/Strata/blob/main/docs/INTEL.md) does compare its Coder IQ1_M GGUF on the same Arc: 78.2 tokens/s for the Strata SYCL engine on a short prompt versus 23–25 for llama.cpp SYCL. This is evidence that a specialized engine can outperform llama.cpp **in that reported setup**. The Strata path used its MTP draft layer while the llama.cpp path did not, so the comparison does not isolate expert-placement policy; it also does not transfer to NVIDIA/Kimi.
- [Maya's README](https://github.com/mw00/project-maya/blob/main/README.md) reports 14.5–118 decode tokens/s across different machines, GPUs, and Maya quant sizes. These are examples of operating GLM-5.3-Flash, not controlled llama.cpp comparisons on this host or our Kimi file.
- Strata and Maya both rely in part on ggml/llama.cpp code or formats. We should credit those components when discussing their throughput. [Strata credits](https://github.com/Niko1221/Strata/blob/main/docs/HOW_IT_WORKS.md), [Maya credits](https://github.com/mw00/project-maya/blob/main/README.md).

## Proposed experiments

1. **Policy gain on the existing Kimi GGUF (primary proof).** Keep the exact local GGUF hash, pinned llama.cpp build, RTX 5070 Ti, prompt template, context, sampling, and output limits. First test only knobs that the installed llama.cpp build actually supports; measure engine automatic fitting, the current `n_cpu_moe` placements, and any new documented cache/offload knob separately. If proposing adaptive *per-expert* placement, implement and validate the engine support first. Do not label a configuration-only change as the Strata/Maya algorithm.
2. **Strata engine comparison (separate model track).** Run a supported Qwen3.8-Flash-Next quant under a pinned Strata release and, if the same GGUF can be loaded, a pinned llama.cpp release on the same host. Record the model and file hashes, draft-layer availability, KV precision, prompt cache behavior, context, output cap, tokenizer/template, and quality checks. Report both native end-to-end throughput and an ablation with drafting disabled where supported, so expert-tier and speculative gains are not conflated. Strata's [bench protocol and raw reports](https://github.com/Niko1221/Strata/tree/main/bench/results) provide a starting format; use fresh prompts because its caches adapt.
3. **Maya runtime calibration (separate model track).** First verify native Windows or a supported Linux host, NVMe free space, and memory headroom; its documentation says WSL2 is unsupported and Maya-S is 96.5 GB. Run the published `--bench`, then `--calibrate`, compare before/after on untouched prompts and repeat runs. Save the selected environment variables, expert hit rates, physical SSD reads, PCIe share, CPU lane timing, time to first token, prefill/decode rates, and peak RAM/VRAM. This tests whether Maya's tuning helps *its own* GLM model on this hardware; it is not a Kimi comparison. [Requirements and bench](https://github.com/mw00/project-maya/blob/main/README.md), [calibration protocol](https://github.com/mw00/project-maya/blob/main/docs/SETTINGS.md).

Across tracks, use the same machine state as far as possible; alternate run order; separate cold-start and warm-cache results; use multiple prompt lengths (short, 4K, 32K, and a longer context when supported), output lengths, and concurrency levels; and preserve every response, failure, raw timing, GPU/RAM/SSD sample, source revision, exact command, and decision in Atlas. A policy is accepted only after it beats the matched engine baseline on reserved workloads while satisfying quality and resource limits. Cross-model throughput belongs in separate charts, never one speedup ratio.
